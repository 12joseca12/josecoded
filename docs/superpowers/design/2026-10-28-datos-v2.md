## 1. Objetivos y no-objetivos

**Objetivos.** (a) Un esquema que sirva las pantallas reales de PANT v2.0 con una consulta por bloque y sin RLS cara; (b) `get_advisors` **sin ningún hallazgo** de seguridad ni rendimiento tras aplicar; (c) superficie mínima: `anon` no toca nada salvo lo explícitamente público, todo lo privilegiado pasa por RPC `security definer` con grants explícitos o por el gateway con la clave secreta; (d) todo verificable en local con `supabase start`, seed y tests RLS con cuatro cuentas.

**No-objetivos.** Migrar datos de josedev; mantener contratos del gateway cuyas tablas desaparecen (ver §9); Radar y newsletter (se diseñan aquí solo en lo que condiciona al lanzamiento: `contact_id`, eventos del outbox, jobs; sus tablas llegan en las fases 7 y 10 con sus specs).

## 2. Principios de diseño (aplican a toda migración)

| # | Principio | Cómo se cumple |
|---|---|---|
| P1 | **Mínimo privilegio por defecto** | `alter default privileges for role postgres in schema public revoke all on tables/sequences/functions from anon, authenticated` en la migración 0. Cada tabla y función recibe sus `grant` explícitos en su migración. `anon` solo tiene `select` en `blog_comments` (filas `approved`) y `execute` en nada. `graphql_public` fuera de `[api] schemas`. |
| P2 | **RLS en todas las tablas de `public`**, políticas por operación (`select`/`insert`/`update`/`delete` separadas, sin `for all`), una política por rol-acción (sin «multiple permissive policies»). | Advisor `multiple_permissive_policies` y `rls_disabled_in_public` limpios. |

## 3. Esquemas y extensiones

- `extensions`: `pgcrypto` (ya), `citext` (emails), `moddatetime` **no** (se usa un trigger propio en `private` para no depender de una extensión en políticas), `unaccent` (normalización de nombres de organizaciones; si no estuviera disponible, `name_normalized` lo calcula el gateway/TS y la RPC lo recibe). **Sin `pg_net`, sin `pg_cron`** (el cron es el del gateway, `*/5`).
- `public`: 24 tablas del lanzamiento (§4), RPC públicas (§6), sin vistas.
- `private`: helpers, `quota_counters`, `scheduled_jobs`, `outbox`, triggers. `revoke all on schema private from public, anon; grant usage on schema private to authenticated, service_role`.
- `storage`: bucket `client-assets` (§8.3). `vault`: vacío en el lanzamiento (§8.5).
- API: `[api] schemas = ["public"]`, `max_rows = 200`, `extra_search_path = ["public", "extensions"]`.

## 4. Tablas del lanzamiento (D46: público + área + CRM)

Convenciones de la tabla: `id uuid pk default gen_random_uuid()` salvo que se diga; `created_at timestamptz not null default now()`; `updated_at` donde hay `set_updated_at`. **Grants** indican a quién se le da `select/insert/update/delete` a nivel de tabla; la RLS afina las filas. `service_role` tiene todo siempre (bypass RLS).

```sql
create or replace function private.is_admin() returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (select 1 from public.staff_members s
```

### 8.4 Notificaciones: outbox + gateway (sustituye a `pg_net` + Edge Function `notify`) — Q2

**Propuesta.** Las filas de `private.outbox` las escriben triggers y RPC (`enqueue`). El gateway, en su cron `*/5` (job `outbox.drain`, ya existe el despachador de 1.7), llama a `outbox_claim(50, worker_id)`, entrega cada evento por Telegram (bot existente) o email (Resend) y hace `outbox_ack`/`outbox_fail`. Los eventos que nacen en el gateway (`lead.created` desde `POST /leads`, `chat.*`) **se notifican en la misma petición** y además quedan en el outbox como respaldo idempotente (clave `payload->>'id'`): el aviso de un lead sigue siendo inmediato; comentarios, subidas y ampliaciones llegan con ≤ 5 min.

**Por qué.** Elimina `pg_net` (advisor `extension_in_public` heredado), la Edge Function (Deno, despliegue aparte, `verify_jwt = false`, secreto compartido en `vault`), el secreto `NOTIFY_SHARED_SECRET` en tres sitios y una vía de salida HTTP desde la base. Un solo lugar con secretos (el gateway), un solo runtime, reintentos observables en una tabla. **Descartado:** mantener `notify` (más piezas y un `security definer` que hace HTTP); Database Webhooks del dashboard (también `pg_net`, configuración fuera del repo); Supabase Queues/pgmq (misma idea con una extensión más; se puede adoptar después sin cambiar el contrato `claim/ack`).

**Qué guarda cada `content_kind`** (zod en `@josecoded/types/content.ts`, validado en la Server Action **y** repetido en `content_publish()` con `jsonb_typeof` básico):
- `message_override` (`key` = ruta de la clave, `locale`): `{ value: string }`. - `faq` (`key` = id estable, `locale`): `{ via: 'hourly'|'fixed'|'packs'|'hiring'|'partners', question, answer, sort, published: boolean }`.
- `project` (`key` = slug, sin `locale`): `{ es: {oneLiner, challenge, work, result}, en: {...}, published: boolean, sort }`. create or replace function private.owns_contact(p_contact_id uuid) returns boolean
```sql
language sql stable security definer set search_path = '' as $$
  select private.is_closer() and exists (select 1 from public.crm_contacts c
                 where c.id = p_contact_id and c.owner_id = (select auth.uid()));
$$;
create or replace function private.owns_client(p_client_id uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select private.is_closer() and exists (select 1 from public.clients cl join public.crm_contacts c on c.id = cl.contact_id
                 where cl.id = p_client_id and c.owner_id = (select auth.uid()));

language sql immutable set search_path = '' as $$ select p_status not in ('won', 'active_client') $$;
```

### 14.5 Publicación de contenido al repo (D53): mecanismo elegido y descartados

**Elegido: Supabase como editor (borradores, versiones, vista previa) + publicación por commit al repo mediante la GitHub App `josecoded-bot` desde el gateway + build estática.** `content_publish()` deja el snapshot en `site_content_publications`; el job `outbox.drain` entrega `content.publish_requested` al handler `contentPublish` del gateway, que con la Git Data API crea blobs, árbol y **un único commit** `content: publish <n> entries (<publication_id>)` sobre `main` (reintento una vez si la ref avanzó), con los ficheros: `content/overrides/messages.es.json`, `content/overrides/messages.en.json`, `content/overrides/faq.json`, `content/overrides/projects.json`, `content/overrides/settings.json`, **`content/pricing.json`** (catálogo de precios completo, v1.4 Q23; §14.12.3), `content/blog/<slug>.<locale>.md` (uno por post publicado; los no publicados se eliminan del árbol). `deploy-production.yml` corre como con cualquier push a `main` (`pnpm generate` fusiona `messages/<locale>/*.json` + overrides → `content/generated/messages.<locale>.json`; `i18n:check` valida que toda clave de override exista y no introduzca `{{DATO}}`; la build falla si algo no cuadra). El job `content.poll_deploy` (`*/5`) consulta el estado del run de Actions del `commit_sha` por la App y marca `deployed`/`failed`; el admin ve «Publicado · desplegado hace 6 min» en D2 y recibe Telegram (`content.deployed` / `content.deploy_failed`). **Vuelta atrás**: `content_rollback` (versión anterior → nueva publicación) o, en emergencia, `git revert` del commit del bot por el controlador.

Por qué cumple las cuatro condiciones: **seguridad** (solo admin con `aal2` escribe; la clave privada de la App vive solo en `wrangler secret` del gateway con permiso `contents:write` sobre este repo; CI no tiene credenciales de Supabase, como exige §8.2); **rendimiento** (cero consultas a la BD en páginas públicas: siguen siendo estáticas servidas por `ASSETS`); **SEO** (texto en el HTML prerrenderizado); **vuelta atrás** (historial en `site_content_versions` y en git). Coste: 5–8 min entre «Publicar» y producción (lo muestra la pantalla), y la GitHub App debe existir antes del gate (ya era insumo de la fase 10; se adelanta).

**Vista previa** sin desplegar: **Draft Mode de Next** (`draftMode().enable()` en una Server Action admin → cookie `__prerender_bypass` → las páginas públicas se renderizan dinámicamente solo para esa sesión). `i18n/request.ts`: si `draftMode().isEnabled` **y** la sesión es admin (`requireAdmin`, doble llave: la cookie sola no basta), carga `content_draft_snapshot(locale)` y la fusiona sobre los mensajes generados; banda «Vista previa de borradores · Salir». Si OpenNext no honra el bypass en `wrangler dev` (riesgo medido en 6.15 paso 1), respaldo: ruta dinámica `/admin/contenido/vista-previa/[...path]` que compone la misma página con los mensajes del borrador, `force-dynamic`, `noindex`, admin.

**Descartados.** (1) Leer `site_content` en cada petición con caché KV: convierte en dinámicas páginas que hoy son estáticas, cuesta CPU en Workers Free y acopla el público a la BD. (2) ISR con `revalidateTag`: exige cambiar `incrementalCache` a R2 + cola en Durable Objects + caché de tags (D1/KV), tres piezas nuevas de infraestructura y la aserción «sin ISR» del DT; no en 3 días. (3) Que Actions lea Supabase para construir: credenciales de producción en CI (prohibido en §8.2). (4) Editar el repo con un PAT: ya descartado en el plan v2.1 a favor de la App. (5) PR + auto-merge en vez de commit directo a `main`: `main` no está protegida y Jose trabaja directo en `main` desde el 2026-10-29; si vuelve la protección, el handler pasa a abrir PR con auto-merge (una línea de configuración).

### 14.12 Decisiones de Jose a Q21–Q24 (2026-11-01) y su diseño

> Sustituye a las recomendaciones provisionales de spec §0.14 (ahora cerradas). Q21, Q22 y Q24 ajustan lo ya descrito en §14.1–§14.10 (los cambios puntuales están marcados «Q21/Q22/Q24» arriba); **Q23 cambia la recomendación** y añade un bloque de esquema: el catálogo de precios se gestiona desde el admin.

#### 14.12.1 Q21 — Comisión = % de lo cobrado, fijado por closer al crearlo y congelado por comisión

- La comisión es un **porcentaje del importe cobrado por la oportunidad** (`p_amount` de `admin_close_lead_paid`), nunca fijo por pack ni escalonado. Extras y ampliaciones **no** generan comisión automática (si Jose quiere pagarla, el admin la crea a mano: RPC `admin_commission_create(p_closer_id, p_lead_id, p_base_amount, p_note)` que aplica la tasa vigente; `uq lead_id` sigue: una por oportunidad).
- La **tasa se fija al crear el perfil del closer**: `admin_staff_invite(p_email, p_role, p_commission_rate)` con la tasa **obligatoria** (`numeric(5,2)`, `0..100`), guardada en `staff_invites.commission_rate` y copiada a `staff_members.commission_rate` por `claim_staff_access()`. En D1 el campo no tiene valor por defecto (el admin lo escribe; la hoja sugiere «habitual: 10 %» solo como ayuda). `admin_staff_set` puede cambiarla después.
- **Snapshot:** `closer_commissions.percent` toma `staff_members.commission_rate` **en el momento de crear la fila** y no se recalcula nunca (`amount = round(base_amount * percent / 100, 2)` en la misma inserción; ambas columnas `not null`). Un cambio de tasa posterior solo afecta a comisiones futuras. Test en §14.9.4.

#### 14.12.2 Q22 — Filas en conflicto con la cartera de otro: el admin decide

- **Flujo:** la RPC de importación deja la fila en `crm_import_conflicts` (tabla en §14.2) sin tocar el contacto existente. El importador ve en K4 «N filas pendientes de revisión del administrador» y, en el historial, cada fila **suya** con su estado (`pendiente` / `resuelta: asignada a ti` / `resuelta: no asignada`), **nunca** quién es el otro dueño ni el id del contacto (grant por columnas). El admin recibe `crm.import_conflicts` por Telegram y resuelve en K4 (pestaña «Conflictos», solo admin) viendo las dos caras: la fila importada y el contacto existente con su dueño.
- **RPC** (`security definer` en `private`, wrapper en `public`, admin):
  - `admin_import_conflicts(p_status conflict_status default 'pending') returns table(id, import_id, importer_user_id, importer_name, row jsonb, existing_contact_id, existing_display_name, existing_kind, existing_status, existing_owner_id, existing_owner_name, created_at)` stable: la lectura completa que el grant por columnas niega a cualquier JWT.
  - `admin_import_conflict_resolve(p_id uuid, p_resolution conflict_resolution, p_note text default null) returns void`: exige `pending`; en una transacción:
    - `assign_existing` (asignar a A): el contacto sigue con su dueño, la fila importada **se descarta**; interacción `note` en el contacto («conflicto de importación: se mantiene»).
    - `assign_importer` (asignar a B): `update crm_contacts set owner_id = importer` + relleno de columnas vacías con `row` (`coalesce(old, new)`) + fusión de `tags`; interacción `note` «reasignado por conflicto de importación»; `created_count`/`updated_count` del import **no** cambian (la fila consta como `conflict`).
    - `merge`: el contacto sigue con A y gana los campos vacíos y las etiquetas de la fila; interacción `import`.
    - `discard`: nada cambia; se cierra.
    - Siempre: `status = 'resolved'`, `resolution`, `resolved_by/at`, `resolution_note`; `enqueue('crm.import_conflict_resolved', {conflict_id, owner_id: importer, outcome: p_resolution = 'assign_importer' ? 'assigned' : 'not_assigned'})`. Si el contacto existente fue borrado o archivado entre medias, la RPC lo trata como `assign_importer` creando el contacto nuevo para el importador (caso raro, documentado en el test).
- **Contadores:** `admin_counters().import_conflicts_pending`; `crm_my_counters().conflicts_pending` (los propios del closer).
- **Idempotencia:** repetir el mismo CSV devuelve el import anterior, incluidos sus conflictos (no se duplican filas en la cola). Un CSV distinto con la misma persona en conflicto → segunda fila `pending` (el admin verá dos; `uq (import_id, row_index)`).

#### 14.12.3 Q23 — Catálogo de precios gestionado desde el admin (packs, extras, presupuestos a medida); Supabase edita, el repo publica

#### 14.12.4 Q24 — TOTP obligatorio también para closers

- `requireStaff()` (web) exige `aal2` **siempre** (misma excepción `ADMIN_REQUIRE_MFA=false` solo local/E2E); sin factor → `/perfil/seguridad` para enrolar; con factor y `aal1` → verificación. Gateway: middleware **`requireStaff`** (nuevo, junto a `requireAdmin`) para cualquier ruta que acepte un JWT de closer (hoy: `POST /api/v1/notify/test` sigue siendo admin; `crm/drafts/*` de 6.8 y Radar más adelante): `staff_members` activo **y** `aal2`, 403 `mfa_required` si no.
- **RLS no ve `aal`**: las políticas con `is_closer()` protegen las filas, pero un JWT `aal1` de un closer con factor enrolado podría llamar a PostgREST directamente. Mitigación aceptada (misma que Q3): la web y el gateway son los únicos clientes previstos y rechazan `aal1`; la clave publicable no otorga nada que RLS no permita; se revisa si Supabase expone `aal` a las políticas (hoy solo `auth.jwt() ->> 'aal'`, que **sí** podría usarse: queda como mejora opcional `private.is_aal2()` en las políticas de escritura del CRM, no en el lanzamiento, porque los tests locales no enrolan TOTP).
- D1 muestra `mfa_enrolled` por persona; el correo `staff.invited` dice que el primer acceso pide un autenticador.
