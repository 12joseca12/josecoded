# Rol de Omen en josecoded: ¿hace falta el backend casero?

**Fecha:** 2026-10-31 · **Autor:** `arquitecto` · **Estado:** propuesta para decisión de Jose · **Responde a:** «Si usamos Supabase y Cloudflare, ¿no es necesario tener el backend en Omen? ¿Con tener solo la IA es suficiente?»

## 0. Respuesta corta

**Sí: para lanzar josecoded no hace falta Omen, ni siquiera para la IA.** Toda la IA del plan (generador 3.7, chat 4.4, borradores del CRM 6.8, Radar 7.x) corre en **Workers AI (Llama 3.3 70B) detrás de AI Gateway**, en Cloudflare (D5, D22, Q9). Nada público consulta Ollama ni el worker Fastify de Omen; los datos viven en Supabase y los avisos salen del gateway (`private.outbox` → Telegram, DATOS Q2). Lo único que hoy toca Omen desde el código es un semáforo de estado del propio Omen y un proxy de desarrollo. La corrección a la pregunta es de matiz: **«solo la IA» tampoco hace falta en Omen**; la IA ya está en Cloudflare. Omen conserva sentido únicamente para lo que un Worker no puede hacer (navegador con IP residencial, Proton Bridge, la CLI de Claude), todo post-lanzamiento y todo con alternativa.

**Lo que un portátil doméstico cuesta aunque no se use mucho:** punto único de fallo (corte de luz, ISP, hardware viejo), consumo 24/7 (≈ 15–30 W ≈ 25–50 €/año), un túnel y un bearer token que exponen la LAN (Samba) si el worker se compromete, y una regla «servicios preexistentes intocables» que convierte cada tarea `infra` en un gate. Todo eso para un lanzamiento que no lo necesita.

## 2. Recomendación

1. **Omen deja de ser dependencia del producto. Se conserva tal cual** (Jose lo usa para otras cosas; nada se apaga ni se toca) pero **el gateway funciona sin él**: `WORKER_URL`/`WORKER_INTERNAL_TOKEN` opcionales, rutas que lo usan solo si está configurado, y producción **sin configurarlo**. Se retira la rotación de `WORKER_INTERNAL_TOKEN` de 9.4 y el token deja de ser secreto obligatorio en `DEPLOY.md`.
2. **IA: solo Cloudflare.** Workers AI + AI Gateway para todo; sin respaldo en Omen (D22 se recorta a «reintento + fallback de modelo en AI Gateway + R7»).
3. **Analítica al lanzar: Cloudflare Web Analytics.** Umami sale de la fase 8; si Jose quiere embudos, Umami Cloud antes que Omen (decisión Q2 abajo).
4. **Radar (post-lanzamiento): sin fase 8.** LinkedIn sigue solo por alertas de correo (Q13); Workana corre en el **Mac** con el mismo runner y patrón launchd que Indeed; n8n, el túnel `n8n.josecoded.com` y Access desaparecen del módulo. Omen solo si el Mac demuestra no bastar, y con datos.
5. **Newsletter (si se activa a los 3 meses): runner en GitHub Actions** como opción principal del spike 10.0; Omen plan B.
6. **Qué sí justificaría Omen en el futuro:** Proton Bridge (Q12), scraping con sesión si Jose activa LinkedIn y el Mac no está disponible a diario, y un LLM local si algún día hubiera que procesar texto que no deba salir de casa. Ninguno está en el lanzamiento.

**Enfoques descartados.** (a) *Mantener el plan tal cual* (Omen como runtime de Umami, Radar y newsletter): tres runtimes que vigilar y cuatro gates de infra para funciones post-lanzamiento. (b) *Pasar a Workers Paid* para Containers y Queues y así absorber scraping y colas en Cloudflare: 5 $/mes + consumo, contradice la decisión del 2026-10-02 y la IP de datacenter no sirve para LinkedIn/Workana. (c) *Apagar Omen*: no es asunto de josecoded; el servidor sigue siendo útil para Jose fuera del proyecto.

## Decisiones de Jose (2026-10-31)

- **Q1 Desacoplar:** sí para el backend de la web (tarea nueva 1.8d: gateway y web funcionan sin Omen). **Pero se estudian usos de Omen como el chat de IA** (p. ej. modelo local para el asistente de 4.4 con Workers AI de respaldo): pendiente de un análisis de coste/latencia/fiabilidad antes de 4.4.
- **Q2 Analítica:** **Umami en Omen** (como en el plan, 8.1). Consecuencia: si Omen cae se pierden visitas, no la web; el script de Umami debe cargar de forma asíncrona y tolerar fallo.
- **Q3 Radar:** **se mantiene en Omen** (radar-runner + n8n + túnel + Access, como en el plan 7.x/8.x).
- **Q4 Newsletter:** **Omen** (como estaba previsto en la fase 10).

Por tanto la fase 8 (Omen) **no se retira**: se mantiene para Umami, Radar, newsletter y, si sale bien el estudio, el chat de IA. Lo que sí cambia es que **ninguna ruta de producción de la web depende de Omen** (1.8d).
